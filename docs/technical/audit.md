## Authority and open evidence

- Application source, Zod schemas, checked-in workflows, tests and public evidence are the primary implementation record. The technical chapters explain them and link to stable files and symbols.
- Keep 01, 06, 10, 15, 17, 20–21 and 24–30 for product intent, past audits or dated decisions. Treat any implementation examples in earlier architecture, schema or financial documents as historical where the code differs.
- Keep 07, 11, 13, 14, 16, 18, 19, 22, 23 and SOURCES as domain, evidence, operational history or verification context. Start a new operator investigation from the technical reference and follow the existing source of truth for each claim.
- Microsoft catalogue scope is bounded. Some exact model/region/mode rates, licence terms, capabilities or SKU mappings remain unverified. Customer reservations, licences and tenant capacity require their own evidence.
- The repository supplies regression evidence and public smoke checks. Independent penetration testing, tenant deployment certification, complete source availability and a continuous price freshness SLA remain outside that evidence. See the [limitations register](07-limitations.md).
