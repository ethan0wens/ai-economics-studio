# Protected pricing publication

## Operating model

GitHub Actions runs the existing Microsoft refresh at 06:17 UTC daily. Tuesday through Sunday use the daily evidence set. Monday and a manual dispatch use the full evidence set. The preparation job reads Microsoft sources, verifies rates and reconciles evidence. It blocks ambiguous or expired evidence, missing coverage, invalid tiers, schema failures and unsafe price moves. Material changes must pass the independent financial, browser, security and catalogue checks before publishing.

The dedicated GitHub App opens or updates one pull request on `automation/verified-pricing`. Its installation token is short-lived, scoped to this repository and revoked after use. The publisher only stages the generated evidence files, the manifest and content-addressed catalogue snapshots. It checks the expected base, branch, author, head and GitHub Actions result. It requires an active protected PR rule and the current `checks` context before requesting a squash merge. It sends the exact checked candidate SHA in the merge request. No bypass actor is needed. Using an installation identity ensures normal PR checks and the post-merge push workflow can start. The default Actions token cannot reliably provide that chain.

The ordinary main-branch deployment workflow is the only production promoter. It builds the approved revision, identifies the previous Worker version, checks the Custom Domain, verifies exact live bytes and catalogue SHA-256, and runs Chromium. GitHub publication and Cloudflare promotion are separate. A failed deployment leaves main ahead and restores the last verified Worker when the candidate is still active. The hourly production check retries genuine drift from the checked current main and skips a coherent live release. It also skips a main change limited to the approval record if the approved revision is still live. The production concurrency group serialises attempts. A stale candidate or a concurrent provider deployment stops without replacing the newer revision.

## One-time owner setup

1. In **Repository → Settings → Rules → Rulesets → Protection Main**, keep enforcement **Active** on `main`. Enable deletion protection, force-push protection, required PRs and linear history. Set required approvals to **0**, turn off **Require review from Code Owners**, **Require approval of the most recent reviewable push** and **Require additional approval for changes made by an unrecognised author**. Add required status check **checks** with **GitHub Actions** as its source. Enable **Require branches to be up to date before merging**. Keep required deployments disabled. Remove unrestricted Codex, general administrator and publisher bypasses where practical. Check **Settings → Branches** for overlapping protection. In **Settings → General → Pull Requests**, enable squash merging.
2. In **Account → Settings → Developer settings → GitHub Apps**, create a private App owned by the maintainer. Disable webhooks and leave organisation and account permissions unset. Set repository **Contents** to **Read and write**, **Pull requests** to **Read and write**, and **Actions** to **Read-only**. GitHub provides Metadata read automatically. Configure installation for the owning account only, install on **Only select repositories**, and select **ai-economics-studio**. Leave the App off every ruleset bypass list.
3. In **Repository → Settings → Environments**, create **pricing-publisher**, and allow deployment from the selected branch `main`. Leave required reviewers and wait timers off. Add environment variable `STUDIO_PRICING_APP_ID` with the App ID and environment secret `STUDIO_PRICING_APP_PRIVATE_KEY` with the private key PEM. Keep Cloudflare credentials exclusively in **production**. That environment must also permit the protected `main` workflow to deploy automatically after a validated pricing merge. GitHub can keep a read-only default Actions token and restrict built-in Actions PR creation.
4. Rotate the App key in **Developer settings → GitHub Apps → App → Private keys**. Generate a replacement, update the environment secret, verify it can mint a scoped installation token, then revoke the old key. Invalid credentials fail the publishing job and report an exception. The next run obtains a fresh installation token. Leave any unmerged candidate in the dedicated branch until recovery.
5. After merging the engineering PR, verify the **Verify Azure retail feed before release** rehearsal and the public production receipt. Check the first scheduled run with a genuine material change. Record the scheduled run, App-authored PR, required checks, protected squash commit and matching production workflow and receipt. A no-change run records its successful check and keeps the existing deployment. If no real change is available, a separate disposable repository and a limited install can exercise GitHub PR and merge behaviour without modifying production prices. Record that result separately from production publication.

The App permissions are repository-wide within their categories. The publisher’s allowlist and exact-revision checks run in the reviewed main workflow. The GitHub ruleset, App protection and production credentials are separate controls. Ordinary contributors still use a feature branch, PR, required checks and owner merge.

## What happens in common cases

| Situation | Behaviour |
| --- | --- |
| No material change | No commit, PR or deployment. GitHub Actions records the freshness check. If a superseded pricing PR is open, the App can close it after confirming identity and base. |
| Evidence renewal | A genuine renewed verification within seven days of expiry is publishable. Routine timestamp churn alone leaves the live catalogue in place. |
| Pending PR or main advanced | Reuse the single App-authored PR. Create a normal fast-forward commit on its candidate branch. If the base moved during validation, different evidence must be regenerated by the next scheduled run. |
| Transient network, rate limit or check startup issue | Bounded retries for source and GitHub reads. Cancelled, timed-out or missing checks can start one new run on the same validated tree. GitHub checks that fail validation halt publication. An incomplete PR is picked up by the next refresh. |
| Invalid data, permanent review issues or denied merge | Stop. Keep the published catalogue and Worker. GitHub Actions and deduplicated maintenance issues provide diagnostics. |
| Deployment failed after merge | The production run records that the new main revision is unverified. Guarded rollback verifies the previous Worker bytes and receipt. The scheduled drift check retries the latest main if it is still ahead. |
| Unexpected Worker, active deployment, catalogue hash or path | Stop and preserve the last independently verified state. Review the indicated mismatch before changing bindings, credentials or scope. |

The PR path was selected because GitHub enforces checks and records the merge without giving the publisher general main bypass. The fallback direct-push bypass would carry repository-wide bypass privileges that GitHub does not constrain by file. The built-in Actions token path also cannot guarantee the downstream triggers.
