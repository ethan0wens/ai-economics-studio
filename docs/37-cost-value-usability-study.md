# Moderated study for cost, value and design review

## Participants and setup

Recruit three to five participants who have never used the studio. Include business stakeholders and technical or FinOps practitioners. Aim for a 35-minute session. Use a current test build and a fictional environment, accounts and rates where needed. Record task results and anonymised observations only. Ask before capturing screens. Keep actual salaries, agreements, customer names and deployment information out of the session.

Start from Home in a fresh browser profile. Let the participant choose desktop or mobile. Repeat the comparison and review tasks in a narrow viewport for at least one session. Use a separate fixture with a verified incompatibility, an unresolved cost and a declared identity policy. The moderator can use the fictional browser cases as a setup reference.

## Task cards

| Task | Prompt for the participant | Observable success |
| --- | --- | --- |
| A · First useful estimate | Set up a Foundry support assistant and estimate what it might cost. Then share the estimate. | Starts from Home, uses Guided, gets a useful estimate or explains missing rates, and exports without entering value or governance. |
| B · Copilot Studio | Model a Copilot Studio support agent with the monthly credits supplied on the task card. | Uses the declared credits. Explains where a credit quantity is needed. |
| C · Compare a change | Explore what might happen if the Foundry workload runs twice as often. | Finds Explore changes, interprets current and proposed cost, and leaves the original estimate intact. |
| D · Explore value | Using the fictional assumptions supplied by the moderator, estimate released time and decide which results can be described as savings. | Explains gross and realised hours, and distinguishes economic equivalent from separately declared cashable savings. |
| E · Change adoption | Compare lower and higher adoption first on their own, then using an explicit workload link. | Identifies why cost remains unknown before linkage and describes which assumptions drive the cost after linkage. |
| F · Review the design | Show a collaborator what is connected, what needs technical confirmation and what control has been declared. | Finds architecture, an incompatible or unverified item, a declared control and the input to review. |
| G · Share evidence | Create a shareable report that separates accepted value from AI spending. | Chooses a format and explains how accepted assumptions and illustrative comparisons are included. |

For tasks D and E, use fictional planning numbers such as 200 target users, 50% adoption, 20 tasks per active user each month, 12 minutes saved per task, 60% realisation and £25 per realised hour. The expected 100 users give 400 gross hours, 240 realised hours and £6,000 monthly economic equivalent. Leave cashable savings blank first. For the explicit linkage, use a dedicated Foundry PAYG usage profile with calls and tokens present and 10 interactions per active user each month. Read cost results from the pinned fixture and compare actual numerators and unresolved counts.

## Observation and decision sheet

Record anonymous participant code, role category, device, test revision, elapsed time to first useful estimate, unnecessary choices, help requests, backtracks and task outcome. Ask the participant where they would find each next action, which costs remain unresolved, whether a declared control is verified, and whether released time means cash savings. Record their own explanation before offering guidance.

Mark each task as independent, assisted or blocked. Flag recurring confusion between the current estimate and a preview, between economic value and cash savings, or between a declaration and validated implementation. Re-test any resulting change before treating the issue as resolved. Compare time to first useful estimate and blocked sessions against a baseline run where available. Use observations from this small sample to guide review of specific journeys.
