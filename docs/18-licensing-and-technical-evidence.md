## Licensing and existing expenditure

[The product inventory](../catalogue/scope.json) includes UK Microsoft 365 Business, Enterprise, Office 365, Copilot bundles and add-ons, Agent 365, Microsoft Entra plans, Defender products and Purview. Where the exact product, GBP price, annual term and VAT treatment were observed together, the [commercial review file](../catalogue/commercial.json) includes a monthly per-seat equivalent. Promotional “starting at” figures, customer programme rates, unverified standalone rates and Purview workload pricing remain manual. PAYG Sentinel and Copilot Studio are separately modelled consumption. Only exact terms and active evidence qualify as public rates.

[Entitlement rules](../catalogue/entitlements.json) record the exact catalogue offer IDs, UK market, relationship, condition, source and review window. Verified inclusions cover such cases as Entra ID P1 in Microsoft 365 E3, Entra ID P2 in E5, and Agent 365 in E7. Copilot add-ons and Entra Suite receive explicit prerequisite checks. Agent 365 eligibility, Purview workload coverage and Defender XDR signal coverage require additional customer-specific review. A prerequisite appears satisfied in the model only when a recognised base entitlement covers the entire declared population of each assigned group. Partial group overlap, missing assignment counts and unreviewed offer variants remain conditional. Agent links describe applicability. Agent 365 continues to use per-user billing.

An owned entitlement needs a declared monthly spend to contribute to existing expenditure. Enter the total actual cost before replacement, annual agreement value divided by 12 where appropriate. All three project ledger bases use zero incremental cost for owned seats. A public per-seat rate can still appear as reference evidence. Incremental seats use one declared deduplicated total, or the sum of group assignments less explicitly entered repeats. The subtraction is a count of repeat assignments, including multiple repeats of one person. A derived result must cover at least the largest group assignment. Duplicate purchase rows of the same SKU and procurement state remain unresolved unless named, distinct seat pools establish separation. Bundle overlap is a review finding. It does not authorise cancelling licences or automatically reducing expenditure.

A replacement edge requires an existing target, a new purchased entitlement, replacement seat counts and an effective date when the contract stops charging for the replaced seats. The known retained monthly cost is the existing monthly spend less the proportional cost of released seats. Multiple replacements cannot release more seats than the old line holds or reuse more seats than the new line covers. An incomplete active change leaves the old retained cost unresolved. The worksheet is a run-rate comparison as of the assessment date. It does not schedule invoices, account for termination fees or infer that contract changes are permitted.

Copilot credits support a documented **customer declaration** of eligible included usage, its evidence basis and expiry. Enter gross credits, then subtract the active, explicitly declared allowance. Allocate one eligible linked prepaid pool in inventory order, and bill remaining PAYG credits. The current runtime preserves this allocation order across JSON and environment duplication. Linked pools that could cover the same workload require clarification. A licence rule alone never creates a credit allowance. BYOM prompt usage has a separate Foundry account line and does not replace the primary Copilot Studio model.

## Technical compatibility

[The technical evidence catalogue](../catalogue/compatibility.json) distinguishes exact regional deployment tables, model capabilities and platform integration rules. An actual deployment region is an independent input. The priced SKU and its billing region do not establish resource availability. A generic PTU tariff has independent model and version fields. The model fields can distinguish the actual version from a billing label.

- **Verified compatible** means the exact reviewed model/version/SKU/region or scoped feature is supported in current public evidence.
- **Conditionally compatible** means a supported path requires factors such as a project connection, quota, capacity, API selection, same-tenant resource access, networking or permissions.
- **Verified incompatible** covers explicit source exclusions, unsupported modalities and known inconsistent selections. Examples include using the Responses API for Copilot prompt BYOM or using a basic classic agent with private Foundry IQ.
- **Unverified** covers missing data, an unreviewed combination or an expired review. Drafts remain editable.

The reference matrix spans eight exact model versions across six model families, six deployment SKUs and three resource regions (UK South, West Europe and East US 2). Of the 144 combinations in this defined grid, 49 are compatible, 43 conditional, 14 explicitly incompatible, and 38 unverified. Agent/platform and resource evidence is tracked separately. For exact rows, use the source-linked applicability matrix in the technical evidence file. Global and regional deployment modes are separately sourced. Data zone and provisioned rows apply only where their precise regional table establishes availability. Azure OpenAI GPT-4.1 capabilities cover text/image input, text output, structured outputs, function calling and the Responses API at the model level. Agent and tool support are assessed separately. Current Foundry uses connections and project-managed access. Foundry IQ has same-tenant and authentication requirements. Private Foundry IQ requires standard networking with virtual network injection and managed identity. A linked storage or monitoring resource still needs a review of its tier, permissions and network path. Subscription quota, deployable capacity and tenant-specific identity rights cannot be verified in this application. ## Review and test procedures

Record the exact condition and reviewed date for each newly scoped offer, mode and relationship. Separate commercial pricing, availability, entitlement and billed unit verification. Rerun the [read-only evidence survey](../.github/workflows/enterprise-evidence.yml) when reviewing sources. Resolve changed terms and unsupported combinations in Git and run the automated tests before deploying. The survey captures source rows for review. It does not automatically promote rules or refresh review expiry. Rules drop to unverified after their review window, while price refresh and deployment continue through the existing workflows.

The three validation measures remain separate in the dashboard, inspector and reports. A price may be valid for a workload that still needs architecture or licensing review. These are planning findings. Certification, tenant checks and contractual authorisation remain outside the application.
